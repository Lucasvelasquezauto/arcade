## Tarea 1 — Migración de `client_id`

Nueva migración, aparte de la existente: `supabase/migrations/20260903203039_add_client_id.sql`.
No se tocó `20260903193452_create_scores.sql` (Art. 2, una migración es un hecho histórico).

Qué hace:

- `alter table ... add column if not exists client_id uuid` — nullable (ver SUPUESTO 1).
- Índice único `idx_scores_client_id` sobre `client_id` — es la idempotencia: un reintento
  tras una respuesta de red perdida reenvía el mismo `client_id` y la base de datos rechaza
  el duplicado en vez de crear un segundo récord (`docs/specs/core.md` §8.2).
- **No se tocó** la función `scores_force_server_defaults`: solo reasigna `id` y
  `created_at`; nunca mencionó `client_id`, así que ya viajaba intacto desde el cliente sin
  cambiar una sola línea de esa función. Verificado con una inserción de prueba (ver Tarea 2).

## SUPUESTOs

1. **`client_id` es nullable en el esquema, no `not null`.** La tabla ya tenía filas
   anteriores (por ejemplo, el registro de prueba que se insertó al verificar
   `20260903193452_create_scores.sql`) que nunca tuvieron `client_id`, y no hay forma de
   reconstruirlo retroactivamente. Exigir `not null` habría requerido purgar esas filas o
   inventar un valor, ninguna de las dos aceptable sin instrucción explícita. El índice
   único sigue funcionando: Postgres nunca considera dos `NULL` iguales, así que filas sin
   `client_id` no chocan entre sí ni bloquean la primera fila real que sí lo traiga. El
   cliente real (`walking-skeleton.md` §5) siempre debe enviarlo; la base de datos no puede
   hacer cumplir esa garantía sin perder las filas preexistentes.
2. **Nombres de variable de entorno con prefijo `VITE_`.** El código de `apps/arcade` (rama
   `m1-deploy`, heredado de `main`) todavía **no lee ningún valor de Supabase** — el cliente
   de récords con cola offline es trabajo de una tarea posterior (`walking-skeleton.md` §7,
   paso 5, todavía no implementado sobre esta base). Elegí `VITE_SUPABASE_URL` y
   `VITE_SUPABASE_ANON_KEY` porque es la convención de Vite para que una variable llegue al
   bundle del navegador (`import.meta.env.VITE_*`); sin ese prefijo, Vite no las expone al
   código cliente y quedarían inaccesibles. Cuando se escriba el cliente de récords, debe
   usar esos mismos nombres, o esta configuración hay que actualizarla.
3. **Team de Vercel: "Lucas Velasquez's projects", no "LAV Games".** La tarea nombra "LAV
   Games" como la organización de Supabase (así es, y así lo verifiqué contra el proyecto
   `tzoikmdsolubcsplofvr`). Para Vercel no se nombró ninguna organización, y la única
   disponible en la cuenta conectada es "Lucas Velasquez's projects" (plan hobby) — ahí
   quedó creado el proyecto.
4. **Se desplegó el `main` que ya existía (`fad2648`), sin mezclar `m1-deploy`.** La tarea
   dice "despliega main"; `main` ya tenía todo lo necesario para `apps/arcade` (Fase de
   `1.10-infra`), y las migraciones de esta rama no son parte del build de Vercel — viven en
   Supabase, no en el bundle de la app. No había necesidad ni instrucción de fusionar
   `m1-deploy` en `main` para cumplir la tarea 3.
