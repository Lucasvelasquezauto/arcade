**Rama:** `m1-core-records` · **Spec:** `docs/specs/core.md` §8–§9 · **Alcance:** solo
récords (§8) y diagnóstico (§9). Bucle, ciclo de vida, entrada, render, audio y hápticos
son de M1.4/M1.5 y no los toqué. Con este cambio, `packages/core` queda completo.

## 2. Variables de entorno que necesito

| Nombre | Para qué | Dónde |
|---|---|---|
| `SUPABASE_URL` | URL del proyecto Supabase | pasada a `createSupabaseRecordsClient({ url, anonKey })` |
| `SUPABASE_ANON_KEY` | Clave anónima pública | idem |

**No las leo yo.** `packages/core` no importa `import.meta.env` ni `process.env` — eso
acoplaría el núcleo a Vite (Art. 3.5: el núcleo es la plataforma, no debe saber con qué
bundler se lo empaqueta). `createSupabaseRecordsClient` recibe `{ url, anonKey }` como
parámetros planos; quien ensambla `apps/arcade` es quien las lee de su entorno y se las
pasa. **SUPUESTO:** el nombre `SUPABASE_ANON_KEY` es mío — `docs/handoff/1.10-infra.md`
solo fijó `SUPABASE_URL` y dejó "la clave anónima" sin nombre de variable. Como
`apps/arcade` usa Vite, y Vite solo expone al código de cliente las variables con prefijo
`VITE_`, en `.env.local` (y en Vercel) deben existir además `VITE_SUPABASE_URL` y
`VITE_SUPABASE_ANON_KEY` — es quien construye el `RecordsService` real en `apps/arcade`
quien debe leer `import.meta.env.VITE_SUPABASE_URL` / `...VITE_SUPABASE_ANON_KEY` y
pasarlos aquí. No confirmé esto en ningún dispositivo real (fuera de mi alcance).

## 3. La interfaz exacta que el shell debe consumir

**Dos capas, no una.** `packages/shell/src/types.ts` ya define `CoreHandle` con
`submitScore(gameId, name)` y `subscribeRecords(gameId, listener)` — esa interfaz **no
cambia** con este trabajo. Lo que entrego aquí es la capa que hace posible construir esa
implementación de `CoreHandle`; ensamblarla (probablemente en `apps/arcade`, fuera de mi
alcance) es el paso que falta.

### Récords

```ts
import {
  RecordsService, createRecordQueueStore, createSupabaseRecordsClient,
  attachAutoFlush, realGenerateClientId, realNowIso,
} from '@arcade/core';

const service = new RecordsService({
  store: createRecordQueueStore(),
  network: createSupabaseRecordsClient({ url: SUPABASE_URL, anonKey: SUPABASE_ANON_KEY }),
  generateClientId: realGenerateClientId,
  now: realNowIso,
});

attachAutoFlush(service); // abrir app + foco + online (§8.3), dispara un flush ya mismo

// CoreHandle.submitScore(gameId, name) — el score sale de la sesión en curso, no de aquí:
async function submitScore(gameId: string, name: string) {
  await service.submit(gameId, name, currentSessionScore);
}

// CoreHandle.subscribeRecords(gameId, listener) es casi literalmente esto:
const unsubscribe = service.subscribeRecords(gameId, listener); // RecordsView es idéntico al de shell/src/types.ts

// El disparador que falta (§8.3, "al terminar cada partida") — llamarlo cuando
// GameModule.readStatus(state) pase a 'over', donde sea que eso se detecte:
service.flush();

// Diagnóstico (§9, "tamaño de la cola de récords"):
service.subscribeQueueSize((size) => diagnostics.setRecordsQueueSize(size));
```

`RecordsView`/`RecordEntry` en `records/types.ts` tienen exactamente los mismos campos
que `packages/shell/src/types.ts` (`{ name, score, achievedAt, confirmed }` /
`{ top10 }`) — no importan uno del otro (dirección de dependencias, Art. 3.4), pero son
estructuralmente el mismo tipo, a propósito.

### Diagnóstico

```ts
import { DiagnosticsRecorder, realNowIso, attachConnectivity } from '@arcade/core';
import { realFrameClock } from '@arcade/core'; // ya existía desde M1.4

const diagnostics = new DiagnosticsRecorder({ now: realFrameClock.now, nowIso: realNowIso });

// Junto a CADA llamada real a loop.onFrame(elapsedMs) — el MISMO elapsedMs:
diagnostics.recordFrame(elapsedMs);

// Envolviendo los LifecycleCallbacks reales, antes de construir el LifecycleController:
const wrappedCallbacks: LifecycleCallbacks = {
  onPause() { diagnostics.recordPause(); realCallbacks.onPause(); },
  onResume() { diagnostics.recordResume(); realCallbacks.onResume(); },
};

attachConnectivity((online) => diagnostics.setOnline(online));
service.subscribeQueueSize((size) => diagnostics.setRecordsQueueSize(size));

// CoreHandle.subscribeDiagnostics(listener) — a la cadencia que se elija (p.ej. 1/s,
// como hace fixtures/fakeCore.ts):
setInterval(() => listener(diagnostics.snapshot()), 1000);
```

`DiagnosticsSnapshot` (`diagnostics/types.ts`) tiene exactamente los mismos campos que
`packages/shell/src/types.ts::DiagnosticsView`.

## 4. Mis SUPUESTO (también como comentario en el código)

1. **`LoopStatsRecorder` no observa `GameLoop` — lo espeja.** La tarea decía
   explícitamente no reescribir el bucle, y `GameLoop` no expone ningún gancho para leer
   "cuántos ticks corrió este frame" desde afuera. En vez de tocar `loop.ts`,
   `LoopStatsRecorder` mantiene su propio acumulador llamando a la MISMA función pura
   `advanceAccumulator` que `GameLoop.onFrame` ya usa internamente — no duplica el
   algoritmo, lo reutiliza. La consecuencia real: quien cablee el bucle de verdad debe
   llamar `diagnostics.recordFrame(elapsedMs)` con el mismo `elapsedMs` que le da a
   `loop.onFrame(elapsedMs)`, y `recordPause`/`recordResume` junto a las llamadas reales
   de pausa — si algún día se desincronizan, las cifras del diagnóstico se desvían de la
   simulación real sin que nada lo detecte. Si esto molesta, la solución correcta es que
   `GameLoop` exponga su propio hook (`onFrame` devolviendo `AccumulatorAdvance`, por
   ejemplo) — cambio de contrato menor que no me correspondía decidir aquí.
2. **Idempotencia de `submitScore` vía `insert` + capturar `23505` (unique_violation),
   NO `.upsert()`.** La migración actual (y la v1.1 de `walking-skeleton.md`, que además
   todavía no está aplicada) solo otorga INSERT y SELECT públicos — nunca UPDATE.
   `.upsert()` de Supabase compila a `INSERT ... ON CONFLICT DO UPDATE`, y Postgres RLS
   evalúa la rama de conflicto contra la política de UPDATE: sin una, un upsert que
   choca de verdad falla. Un `insert` que falla con `23505` en cambio solo significa "un
   intento anterior ya llegó, se perdió la respuesta" — la corrección es releer esa fila
   con SELECT (público), no reescribirla. Esto depende también de que la migración v1.1
   agregue la restricción de unicidad sobre `client_id`, no solo la columna.
3. **`createRecordQueueStore()` cae a un `MemoryQueueStore` si IndexedDB no existe.**
   Ninguna spec pide este fallback — `docs/specs/core.md` §8.1 dice literalmente "en
   IndexedDB". Lo agregué porque la alternativa (lanzar, o silenciosamente no encolar
   nada) viola la regla §8.6 más fuerte: "un fallo de red nunca cuesta un récord ni
   bloquea el juego". Un Safari con IndexedDB bloqueado en cierto modo privado es un caso
   real, no hipotético. El costo es honesto: si la pestaña se cierra antes del próximo
   flush, ese récord en memoria se pierde — pero eso también es preferible a un juego que
   no arranca.
4. **`attachAutoFlush` no cablea "al terminar cada partida" (§8.3).** Este paquete no
   tiene ninguna noción de sesión de juego en curso — eso vive en la composición que une
   `GameLoop` + `LifecycleController` + `GameModule.readStatus`, que **no existe todavía
   en `packages/core`** (ninguna rama anterior la construyó; ver huecos, punto 2). Documenté
   la receta exacta en §3 de arriba para quien la construya.
5. **`mergeRecordsView` agrega el récord pendiente DESPUÉS del top10 confirmado, sin
   reordenar.** §8.4 y §8.5 juntas no dicen dónde va un récord todavía no confirmado en
   el orden mostrado — solo el servidor puede rankearlo, y no lo ha visto. Ponerlo al
   final, en vez de intentar adivinar su posición por puntaje, es la lectura que menos
   se acerca a "el cliente calcula el ranking" (prohibido explícitamente por §8.5).
6. **`SUPABASE_ANON_KEY` es un nombre que invento yo** (§2 arriba) — ningún documento
   anterior lo fijó.
7. **Tope de 10 entradas en `PauseLogRecorder`.** Ninguna spec fija cuántas pausas
   recordar; elegí el mismo número que `RecordsView.top10` por consistencia visual, sin
   research previa (no aplica: no es una constante de fidelidad a un juego).
8. **`RecordsService.submit()` no espera a que la red responda.** Encola, publica la
   vista con el récord pendiente, y dispara `flush()` sin `await`-earlo — así el llamador
   (`CoreHandle.submitScore`) nunca queda bloqueado por la red, cumpliendo §8.6 al pie de
   la letra ("ninguna operación de red está en la ruta de una partida").

## 5. Huecos que encontré en la spec

- **La migración real (`supabase/migrations/20260903193452_create_scores.sql`) es v1.0,
  sin `client_id`.** `walking-skeleton.md` ya lo señala como conocido (v1.1, "pendiente
  de aprobación") y mi tarea me pidió implementar contra v1.1 y anotar la dependencia —
  queda anotada aquí, explícita: **hasta que esa migración se aplique (con columna
  `client_id uuid unique`), `submitScore` fallará** (la columna no existe) y
  `getTopScores` funcionará pero cada `ServerRecordSummary.clientId` vendrá `undefined`,
  lo cual rompe la deduplicación de `mergeRecordsView` (nunca reconocerá un récord propio
  como ya confirmado, así que quedaría duplicado en pantalla hasta que la migración
  exista). No apliqué nada en Supabase (fuera de mi alcance) ni toqué la migración
  (`supabase/` no es `docs/`, pero tampoco es mi paquete).
- **Ningún módulo de `packages/core` compone `GameLoop` + `LifecycleController` +
  `GameModule` en una sola sesión jugable.** M1.4/M1.5 dejaron el bucle, la pausa, la
  entrada, el render y el audio como piezas sueltas; nadie construyó todavía el "quinto
  archivo" que las une (algo como `session.ts`, que sería quien también sabe cuándo
  `readStatus() === 'over'` y por lo tanto cuándo llamar `flush()` por fin de partida).
  Sin ese archivo, tampoco existe hoy una implementación real de `CoreHandle` en ningún
  lado — ni siquiera parcial. Este es el hueco más grande que dejo: records/diagnostics
  están completos y probados, pero conectarlos al shell real requiere ese módulo de
  sesión, que ninguna spec asigna explícitamente a nadie todavía.
- **`core.md` §9 no dice a qué cadencia se debe llamar `subscribeDiagnostics`** (una vez
  por frame, como `subscribeSession`, o algo más barato como una vez por segundo). Elegí
  no decidirlo yo: `DiagnosticsRecorder.snapshot()` es "pull" puro, sin su propio timer,
  y documenté en §3 que 1/s (como ya hace `fixtures/fakeCore.ts` del shell) es razonable.
- **Ninguna spec dice si un récord pendiente debe reintentarse indefinidamente o
  descartarse después de N intentos/tiempo.** Implementé reintento indefinido (cada
  oportunidad real de §8.3 lo vuelve a intentar, para siempre) porque §8.6 ("nunca cuesta
  un récord") no admite ninguna lectura donde un récord real se descarte solo.

## 6. Qué me pareció mal diseñado (o al menos, tenso)

- **El contrato de récords da por sentada una columna que la base de datos desplegada no
  tiene.** Mismo patrón que M1.5 reportó para el manifiesto de sprites/audio: la spec
  (v1.1, walking-skeleton.md) y el código que debe implementarla llegaron antes que el
  cambio de esquema que los hace funcionar de verdad. No es un problema de mi
  implementación — está correcta contra el modelo que se me pidió seguir — pero
  `RecordsService` completo queda **inerte en producción** hasta que alguien aplique esa
  migración a mano en el panel de Supabase (ver `supabase/migrations/README.md`), un
  paso manual que nadie ha ejecutado todavía según puedo verificar desde el repo.
- **Separar "records" de "session"/"CoreHandle" entre agentes distintos garantiza que
  alguien tenga que releer y re-razonar sobre `GameLoop`/`LifecycleController` desde
  cero para unir las piezas.** Habría sido más barato que esta misma tarea incluyera
  también ese módulo de composición (no es récords ni diagnóstico puros, pero es lo único
  que los vuelve útiles) — lo señalo para que el hilo orquestador decida si vale la pena
  una M1.11 explícita para "ensamblar `CoreHandle`" antes de que alguien lo descubra a
  mitad de otra tarea.
- **`RecordsQueueDeps` mezcla dos preocupaciones (persistencia + red) en un solo objeto
  de dependencias** porque `RecordsQueue` y `RecordsService` las necesitan juntas casi
  siempre. Funciona, pero si en algún momento se quiere una cola sin red (por ejemplo,
  para simular en tests de otro paquete), habría que partir la interfaz — no lo hice
  porque nadie lo necesita todavía y hubiera sido especular sobre un caso de uso que no
  existe (regla del proyecto: no diseñar para lo hipotético).
